A stage database, from cluster to migration

Each workload stage has its own stage database on one shared Aurora cluster. Deploy creates it, migrates it, or drops it. The SQL is generated once and applied three ways.

01 · Containment

Where it lives

The shared Aurora cluster is Data API only. The maintenance database tanstackaws holds no person tables. It runs CREATE DATABASE for every stage database and DROP DATABASE only for ephemeral ones. main and prod stay. Person tables live in schema default inside the stage database, and that schema is never named after the stage.

Deploy is what creates, migrates, or drops one of those stage databases.

02 · Lifecycle

What deploy does

AuroraSchemaLifecycle sends a custom resource event to aurora-schema-lifecycle.ts. Create or Update runs CREATE DATABASE on tanstackaws, leaves an existing stage database in place, and applies pending migration.sql. Delete of an ephemeral stage runs DROP DATABASE. Delete of main or prod leaves the stage database in place.

That pending SQL is generated once, then applied three ways.

03 · Migrations

How the SQL arrives

drizzle-kit generate writes packages/aurora/migrations from person-schema.ts. drizzle-kit migrate applies that folder only when the stage database already exists. Workload deploy and migrate-stage-database.ts create it first on tanstackaws, then apply with migrateStageDatabaseSchema.
