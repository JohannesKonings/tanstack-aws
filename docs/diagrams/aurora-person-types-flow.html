Aurora person types and schemas

An Aurora person read passes through four shapes: the Drizzle table, its select schema, a page schema, and a view. Each shape is derived from the one before it, so a field only reaches the screen if every step lets it through. The page schema is the hub. It decides which columns one read may return, and both the SELECT list and the view transform are derived from it.

Walk the flow

One step per band in the diagram, using the person list read as the example. The detail read and the four related reads (addresses, bank accounts, contacts, employments) follow the same pattern.

Band 1 · Tables, select schemas, page schemas

Drizzle table → select schema → page schema

packages/aurora/src/person-schema.ts

The Drizzle table is the storage. createSelectSchema turns it into a Zod schema of one full row; a nullable column such as gender becomes null when it is empty.

A page schema is a pick of the select schema, and the pick is the field list for that read. createdAt and updatedAt stay on the table, but no page schema picks them, so no read returns them. 

export const persons = stageDatabaseSchema.table('persons', {
  id: uuid('id').primaryKey(),
  firstName: text('firstName').notNull(),
  lastName: text('lastName').notNull(),
  dateOfBirth: timestampColumn('dateOfBirth'),
  gender: genderEnum('gender'),
  createdAt: timestampColumn('createdAt').notNull(),
  updatedAt: timestampColumn('updatedAt').notNull(),
});

export const personSelectSchema = createSelectSchema(persons);

export const personListSchema = personSelectSchema.pick({
  id: true,
  firstName: true,
  lastName: true,
  gender: true,
});

Band 2 · Column selections and reads

Page schema → column selection → read query

apps/webapp/src/aurora-persons/aurora-persons.ts

The SELECT list is built from the page schema. pageColumns takes the page-schema keys and looks up the table column with the same name, so no field is written by hand here.

The list cannot miss a field, add an extra one, or point a key at the wrong column. The query row type is the picked columns, so it matches the page schema. 

const pageColumns = <TTable extends Table, TShape extends Record<string, unknown>>(
  table: TTable,
  pageSchema: { shape: TShape },
) => {
  const columns: Record<string, unknown> = getColumns(table);
  return Object.fromEntries(
    Object.keys(pageSchema.shape).map((key) => [key, columns[key]]),
  ) as Pick<TableColumns<TTable>, keyof TShape & keyof TableColumns<TTable>>;
};

const personListColumns = pageColumns(persons, personListSchema);
export const readAuroraPersonList = async (
  client: StageDatabaseQueryClient,
  env: NodeJS.ProcessEnv,
) => {
  const db = stageDatabase(client, env);
  return db.select(personListColumns).from(persons);
};

Band 3 · View transforms and screen types

Read query → parse → view transform → screen type

apps/webapp/src/aurora-persons/view.ts · server.ts

A view is the page schema plus .transform(). The server function runs each row through parse, which checks the row against the page schema and then runs the transform. Components take the transform output, never the page schema.

The transform is where a field can look different on screen. The database speaks null, the screen speaks undefined: every nullable column goes through absent. A display-only field, such as a single name built from firstName and lastName, belongs here too. It exists only on the view, so it cannot be a query key. 

const absent = <T>(value: T | null) => value ?? undefined;

export const auroraPersonListView = personListSchema.transform((person) => ({
  id: person.id,
  firstName: person.firstName,
  lastName: person.lastName,
  gender: absent(person.gender),
}));

export type AuroraPersonListRow = z.output<typeof auroraPersonListView>;
// server.ts
export const getAuroraPersonList = createServerFn({ method: 'GET' }).handler(async () => {
  // ...try/catch for configuration errors omitted
  const rows = await readAuroraPersonList(createStageDatabaseClient(), process.env);
  return {
    persons: rows.map((row) => auroraPersonListView.parse(row)),
    status: 'ready' as const,
  };
});

Extend the flow: add a field

A new field walks the same path from the top band down. The example adds a hypothetical nullable nickname to the person detail read. Skip any step that does not apply: a field that already exists in storage starts at step 2.

Step 1 · Drizzle table

Add the column, then generate a migration

packages/aurora/src/person-schema.ts

Only for new storage. The select schema picks up the column on its own because it is derived from the table. See docs/stage-database.md for generating and applying the migration. 

export const persons = stageDatabaseSchema.table('persons', {
  // ...existing columns
  nickname: text('nickname'),
});

Step 2 · Page schema

Pick the field on each read that should return it

packages/aurora/src/person-schema.ts

Only the page schemas that pick the field will return it. Leaving it off personListSchema keeps the list read unchanged. There is no column-selection step: pageColumns follows the pick, so personDetailColumns selects nickname from here on. 

export const personDetailSchema = personSelectSchema.pick({
  // ...existing fields
  nickname: true,
});

Step 3 · View transform

Map the field onto the screen type

apps/webapp/src/aurora-persons/view.ts

The transform builds a new object, so a field it does not map never reaches the screen. A nullable column goes through absent, like every other nullable column. AuroraPersonDetail updates on its own, because it is the transform output. 

export const auroraPersonDetailView = personDetailSchema.transform((person) => ({
  // ...existing fields
  nickname: absent(person.nickname),
}));
